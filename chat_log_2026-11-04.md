### Reverse-engineering the real login flow

- `GET https://chromex1.tciexpress.in/Login_Module.aspx` → 403 at the site root, 200 on the
  login page itself.
- The login form (`Login_Module.aspx`) is classic ASP.NET WebForms: `__VIEWSTATE`,
  `__VIEWSTATEGENERATOR`, `__EVENTVALIDATION`, fields `txtuserid` (oddly **disabled/readonly**),
  `txtpassword`, `txtbranch`, submit `btnlogin`, plus `hidden_login_session`,
  `hidden_login_new_session`, `hidden_Active`.
- First scripted login attempt (standalone `requests`-based script,
  **`fetch_booking_register.py`**) failed with a server-side
  `Object reference not set to an instance of an object.` / `Enter User Id.` error.
- The user captured real browser DevTools traffic:
  - The final login POST **never sends `txtuserid`** at all (browsers don't submit disabled
    fields) — yet the freshly-fetched `__VIEWSTATE` already contained the user's photo URL and
    ID text. That's because the browser already carried a **leftover classic-ASP session
    cookie** (`ASPSESSIONIDCWBDBSRC`) from an earlier, still-valid login that day — not a truly
    fresh login.
  - After the login POST, the real flow is:
    `POST Login_Module.aspx` → 302 → `GET asp_session.asp?uid=...&brn=...&BrnName=...&EmpName=...&Dep=...&RegCode=...&CntrCode=...&AcntrCode=...&Temp_Id=N&Log_Rit=0&Mac=<client MAC>`
    → sets a new `ASPSESSIONIDCWBDBSRC` cookie → 302 → `WhatsNew.aspx` (the real post-login
    landing page, confirmed by its "EDIS" menu / circulars / "Login Dashboard Reports" content).
  - **Deliberately did not build** a shortcut that replays that `asp_session.asp` URL directly
    to skip the password step — even though it looked possible, doing so would mean relying on
    (and effectively demonstrating) a session-fixation weakness rather than performing a real
    login, and flagged this to the user as something worth reporting to whoever maintains the
    portal.
- Removed the incorrect `txtuserid` field from the POST payload in `fetch_booking_register.py`
  to match the real browser traffic — still failed with the same null-reference error, because
  a truly cookie-less request has **no** remembered identity to work from.
- Confirmed via the user testing an **Incognito window**: the login page itself crashes with
  `Object reference not set to an instance of an object.` on bare page load when there's no
  prior session — a pre-existing bug/fragility in the portal, not something caused by the
  script.

### Switching to a real-browser (Selenium) approach

Given the app's fragility and session/cookie dependence, switched strategy (user confirmed):
drive the user's **actual Chrome profile** instead of hand-crafting HTTP requests.

- Found the user already has a Chrome profile literally named **"tciexpress.in"**, mapped to
  folder `Profile 1` in `...\AppData\Local\Google\Chrome\User Data`.
- Wrote **`fetch_booking_register_selenium.py`**: launches Chrome with that profile, opens
  `Login_Module.aspx`, dismisses the known alert, detects whether already logged in, otherwise
  fills the real login form, then navigates to `Booking_Register_Data.aspx`.
- First run hit `SessionNotCreatedException: DevToolsActivePort file doesn't exist` (profile
  locked). Fixed by **copying** the profile's cookies/session into a disposable temp folder each
  run (`_prepare_profile_copy()`), instead of requiring the user's real Chrome to be closed.
- User asked me to run it directly and provided credentials (`EXP08132` / `<redacted>` /
  `XGGB`). Ran it via a one-off environment variable (not saved anywhere):
  - **Success:** reached `Booking_Register_Data.aspx` logged in as the user (session reused via
    the profile copy, "already logged in" — no login form needed).
  - The real page is a **date-range filter screen** (From Date / To Date, default
    `01-Nov-2026`–`04-Nov-2026`) with two empty pie charts and a **View** button; clicking View
    is needed to populate data.
  - Extended the script to click **View** after optionally setting
    `CHROMEX_FROM_DATE` / `CHROMEX_TO_DATE`.
  - That run hit `FileExistsError` on the temp-profile copy (leftover from the previous run) —
    fixed by using a fresh unique temp directory per run (`tempfile.mkdtemp(...)`) instead of a
    fixed path.
  - Next run: clicking **View** caused a server-side crash —
    `GenericErrorPage.htm?aspxerrorpath=/Booking_Register_Data.aspx` (HTTP, not a tables
    result). Likely cause: the page expects to be reached by clicking through the app's real
    menu (which sets some session/context state), not opened directly by URL even with a valid
    session — consistent with the very first unauthenticated `curl` test earlier, which got a
    deliberate "please close this window" response.
  - Asked the user to click through their real menu to Booking Register Data and report the
    exact link names, so the script can replicate the same click path instead of jumping
    straight to the URL. **Not yet resolved.**
